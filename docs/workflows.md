# Reusable workflows

This page lists what each reusable workflow and composite action in cplieger/ci runs. It is for anyone calling one from their own repository or copying one out.

## The CI entry point

`ci.yaml` checks which files the repository has and runs one job per match. A repository with Go and a web frontend runs both jobs in parallel. The `repo` and `markdown` jobs always run, `pr-policy` runs on every pull request it applies to, and `alerts` runs whenever the repository has an alert rule file. The other jobs run only when the change touches a file other than Markdown, `LICENSE` or `.gitignore`. The `validate` job collects every result, so branch protection needs one required check, `ci / validate`.

| The repository has | Job | What runs |
| --- | --- | --- |
| any files | `repo` | actionlint, zizmor, a gitleaks scan of the working tree, the comment-ratio check, the NOTICE check, and `actions/dashboard-check` on each root `grafana-dashboard.json` and `grafana-dashboard-<suffix>.json` |
| any files | `markdown` | markdownlint-cli2, and lychee offline for internal links and heading anchors |
| `go.mod` at the root | `go` | `go-ci.yaml` |
| a `go.mod` in a subfolder, with tracked Go files | `go-nested` | `go-ci.yaml` once per module folder |
| a Go module whose `go.mod` requires another module of the repository with no `replace` for it | `go-work` | a build and `go test -race` of every module against the other modules' current code, under a `go.work` the job creates and never commits |
| a Go module that tracks a file built for Windows or macOS: a `_windows` or `_darwin` file-name constraint before the name's first dot (`x_windows.go`, `x_windows.pb.go`, `x_darwin_arm64_test.go`), or a `//go:build` line above the package clause naming `windows` or `darwin` as a term that is not negated, in a file Go does not ignore | `go-os` | `go-os-ci.yaml` on `windows-latest` or `macos-latest`, once per module and operating system |
| `jsr.json` at the root | `ts` | `ts-ci.yaml` |
| a `package.json` or `jsr.json` in `static-src/`, `web/`, `internal/server/static-src/` or `internal/webui/static-src/` | `web` | `ts-ci.yaml` in the first folder found, with the CSS and HTML lints on |
| a `package.json` or `jsr.json` in the `web/` folder of a `go-nested` module | `ts-nested` | `ts-ci.yaml` once per such folder |
| a `Dockerfile`, or a root `go.mod` or `jsr.json` and a tracked `.sh` file outside `node_modules`, `vendor`, `testdata` and `dist` | `shell` | `shell-ci.yaml`, with hadolint only when there is a `Dockerfile` |
| any files | `deadset` | `deadset-ci.yaml` at the repository root, and, when the root has a `go.mod`, once per nested Go module folder with tracked Go files |
| `tests/perf/plan.json` | `perf` | `perf-ci.yaml`, [the performance gate](#the-performance-gate), which measures the plan's `pr` set on a pull request or in a merge queue and nothing on a push |
| a `Dockerfile` | `docker`, `docker-arm64` | an image build on `amd64`, and on `arm64` in public repositories, with no push and no scan; the `docker` job also builds each `images/<name>/Dockerfile` beside the `Dockerfile` on `amd64` into the Docker daemon (the release's runner images, below). When that build passes and the repository has a root `go.mod` and a tracked `*_integration_test.go` file, the job then runs the root module's `go test -tags integration` |
| `*.py` files | `python` | Ruff |
| shell scripts or workflow files, and no `go.mod`, `jsr.json` or `Dockerfile` | `scripts` | shellcheck, shfmt, `tests/shell/run.sh` when the repository has one, yamllint, a TOML check, and the probe scripts present in the repository |
| an `alerts/*.yaml` file | `alerts` | `promtool check rules` when `alerts/promql.yaml` exists, `promtool test rules` when `alerts/promql_test.yaml` exists, a LogQL parse of a copy of `alerts/logql.yaml` when that file exists, and, when `docs/monitoring.md` exists, a check that its alert table names exactly the alerts the rule files define |
| a pull request, in a repository whose default branch is `dev` | `pr-policy` | a conventional-commit check of the title, and on a pull request into `main` a check of what its head branch may change |

The `shell` and `scripts` jobs never both run, so no shell script is checked twice.

An edit to `docs/monitoring.md` alone still runs the `alerts` job, so it meets the alert-table check. The alert table is each table on the page whose first column is headed `Alert`, outside code blocks, and a row names its alerts in backticks in that column. The LogQL parse runs `lokitool rules lint` on a copy, because that command rewrites the file it reads.

`go-ci.yaml` runs with `GOWORK=off`, so each module builds against the versions of the other modules that its `go.mod` names, as a consumer's build does. A module that starts using a change to another module of the repository therefore fails its `go-nested` job until that module's change is tagged and the `require` names the tag. The `go-work` job catches the opposite case: a change to one module that breaks another fails there, before either is tagged.

On a pull request in a repository with no root `go.mod`, `go-nested`, `go-os` and `ts-nested` run only for the modules the pull request changes, counted from the commit its merge ref was built on, so a change the base branch gained after the pull request opened adds no module. A moved file counts for both the module it left and the one it entered. Each leg builds against the other modules' tags, so a change to one module cannot change another module's result there. `go-work` still runs for every module.

A changed file outside every module folder keeps every module, unless its path ends in `.md` or is `LICENSE` or `.gitignore` at the root. So does a module that replaces another, or a symlink into another module. A push, such as the merge into `dev`, runs every module.

In `cplieger/ci` itself, a `go-os-canary` job runs `go-os-ci.yaml` over public Go modules that track Windows or macOS files, at fixed commits, on each runner detection selects for them. A change to that workflow or its pins that breaks a real module's Windows or macOS leg fails that job before a release carries it.

After the `amd64` build, the `docker` job runs two optional image tests. The shared smoke harness runs when the repository has `tests/image-smoke.conf`. A repository's own `tests/image-test.sh` runs with the image reference as its first argument, and it must be committed as executable. The release workflow runs both again on the app image it builds, as [the release workflow](#the-release-workflow) describes.

In a repository with runner images, the `docker` job then builds each one on `amd64` in the release's order. It loads each into the runner's Docker daemon as `ghcr.io/<owner>/<image>-runner:<name>-dev` and `<name>-ci`. A test therefore reads the images this commit builds, never a published copy.

The integration tests run when that build passes and the repository has a root `go.mod` and a tracked `*_integration_test.go` file. The job sets up Go from that `go.mod` and runs `go test -tags integration -count=1 -timeout 45m ./...` at the root. They run whatever the app image's tests said, and they reach the daemon at `/var/run/docker.sock`. The job's time limit is 120 minutes with runner images and 15 minutes without. A repository with integration tests but no runner images does not run them here.

## Choosing the runner

`ci.yaml`, `security-scan.yaml` and the five workflows `ci.yaml` calls (`go-ci.yaml`, `ts-ci.yaml`, `shell-ci.yaml`, `deadset-ci.yaml` and `perf-ci.yaml`) take a `runner` input, a runner label that is empty by default. Empty runs every job on `ubuntu-26.04`. `ci.yaml` passes its input on to the workflows it calls, and the synced `ci.yml` and `security.yml` pass the repository's `CI_RUNNER` variable, so setting that variable to a self-hosted runner's label moves the repository's jobs there, and deleting it moves them back.

These jobs stay on GitHub's runners whatever the input says:

- `docker`, which builds the image, and `docker-arm64`, which builds it on `arm64`;
- `shell`, when the repository has a `Dockerfile`, because hadolint runs in Docker;
- `go-os`, on Windows and macOS;
- the `trivy` job of `security-scan.yaml`, which builds the image;
- the `plan` job of `perf-ci.yaml`, which installs cosign with `sigstore/cosign-installer`, a step that needs `envsubst`.

`codeql.yaml` takes no `runner` input. It runs only in public repositories, and its Go build uses the Go that GitHub's image carries.

The jobs that move install their tools into `$RUNNER_TEMP/bin` with no `sudo`, and set up Go, Node and Python with the setup actions, so a runner built from GitHub's runner container image, `ghcr.io/actions/actions-runner`, runs them as a user with no root. A few checks need more on the runner:

- `go test -race`, in `go-ci.yaml` and `go-work`, needs a C compiler.
- A `ts-ci.yaml` package with `@vitest/browser-playwright` needs the system libraries of each engine it tests on, Chromium or those named in `cplieger.browsers`, because on a self-hosted runner the job installs the browsers without their system libraries.
- deadset over a large Go module peaks near 3 GB of memory.
- The performance gate's measure jobs need the system libraries of Chromium and WebKit. Its budgets name the runner they were calibrated on, so on any other runner every metric is reported and none gates.

## The language workflows

| Workflow | What it runs |
| --- | --- |
| `go-ci.yaml` | `go vet`, golangci-lint, `go test -race`, govulncheck, `go mod verify`, a wiregen drift check, dependency review on public pull requests |
| `go-os-ci.yaml` | on the `runner` input's Windows or macOS runner: `go vet`, golangci-lint, `go test -race`, and `go vet` for Linux, macOS and Windows on amd64 and arm64 |
| `ts-ci.yaml` | `npm ci`, ESLint, `tsc`, knip for import cycles and undeclared dependencies, vitest (after building the Go test server a package names in `sseFixture`), fast-check fuzz tests, Prettier, `package.json` and `jsr.json` version parity, a publish-surface check, dependency review |
| `ts-ci.yaml` with `web-lint: true` | the above, plus Stylelint, html-validate and an import-map coverage check |
| `shell-ci.yaml` | shellcheck, shfmt, hadolint on the `dockerfile` input and every `images/<name>/Dockerfile` unless the input is empty, and `tests/shell/run.sh` when the repository has one |

With `web-lint: true`, a package that declares a `lint:web` script in `package.json` runs that script in place of Stylelint and html-validate, so a local `npm run lint:web` is the same check. The script must lint every tracked CSS file with Stylelint and the synced `.stylelintrc.json`, lint every tracked HTML file with html-validate, and exit non-zero when either fails.

`ts-ci.yaml` also runs the tests again on the oldest Node major that `package.json` `engines.node` allows, read with the semver library npm bundles (its `minVersion`), so `>=24`, `^22 || ^20` and `<26 >=22` give 24, 20 and 22. The `package settings` job installs the Node `validate` tests on before that read, so it does not depend on a Node that the runner image ships. The job asks setup-node for the range kept within that major, so it runs on the newest release of the major that the range allows: `~20.1` runs on the newest 20.1.x, not the newest 20.x. A package with no `engines.node`, or a range whose oldest allowed version is older than Node 4 (`*`, `>=0.12`, `<26`), skips that job, and the `package settings` job logs a notice saying which. An `engines.node` that is not a string, not a valid semver range, or satisfied by no version fails the `package settings` job, and the `validate` and `engines-floor` jobs are skipped.

`ts-ci.yaml` splits the tests into shards when the package's `package.json` sets `cplieger.vitestShards`, for example `"cplieger": { "vitestShards": 2 }`. Sync never writes `package.json`, so each branch of a repository sets its own count, and a branch that does not set it runs one shard. The count must be an integer from 1 to 100; any other value, a `cplieger` field that is not an object, or a `package.json` that is not valid JSON fails the `package settings` job, and the `validate` and `engines-floor` jobs are skipped (the `validate` row shows its unevaluated name). Above 1, each job is named `validate (shard <i>/<n>)` and runs `npm test -- --shard=<i>/<n>`, and shard 1 also runs every other check once. The `ci / validate` check passes only when every shard passed. npm appends the `--shard` argument to the end of the `test` script, so a sharded package's `test` script must be a single vitest command, and the job fails when that script does not name vitest or holds a `;`, `&`, `|`, `#` or a newline. A command that has to follow the tests, such as a duration check reading vitest's JSON report, goes in the `posttest` script, which runs in each shard on that shard's report. The `engines-floor` job is split the same way: each job gets the same `--shard` argument and the same single-command rule, and its `posttest` reads that shard's report. It takes no expression name, because GitHub does not evaluate one for a skipped job and most packages skip it, so its rows read `engines-floor (<i>)` when it runs and `engines-floor` when it is skipped.

A package whose tests use Vitest Browser Mode (a `@vitest/browser-playwright` devDependency) gets Chromium by default. It names more engines in `cplieger.browsers`, for example `"cplieger": { "browsers": ["chromium", "firefox", "webkit"] }`. The list must be non-empty and hold each of `chromium`, `firefox` and `webkit` at most once. Any other value fails the `package settings` job. `validate` and `engines-floor` install exactly those engines under a 10-minute step timeout. Chromium installs alone, because the runner image carries its libraries. For Firefox and WebKit on a GitHub-hosted runner, whose image lacks their system libraries, the step first runs Playwright's `install-deps` under a 5-minute bound, so an Ubuntu mirror or DNS outage fails the step after 5 minutes with a message naming it, then installs the engines. A self-hosted runner gets no apt, since it may grant no root, so its image must carry the libraries of every engine a package names, Chromium's included. The weekly Stryker run relies on the same for Chromium. Both jobs export the list to every step as `CPLIEGER_BROWSERS`, comma-separated in that fixed order (`chromium,firefox,webkit`), so the tests, their `posttest` and the fuzz step all see it. The weekly Stryker run installs Chromium alone and sets no `CPLIEGER_BROWSERS`, and neither does a local run, so a vitest config that reads the variable must fall back to Chromium when it is unset.

A package whose tests run against a Go server builds that server first by naming its Go module in `package.json`: `"sseFixture"` is the module directory, relative to the directory holding `package.json`, and the optional `"sseFixtureTags"` is the `-tags` value, for example `"sseFixture": "..", "sseFixtureTags": "my_test"`. A package without `sseFixture` builds nothing. The `package settings` job checks both values, because they come from the branch under test. The directory must resolve inside the checkout, through any symlinks, and hold a `go.mod` file, its `go.mod` and any `go.sum` must not be symlinks leading outside the checkout, and the tags must be letters, digits and underscores separated by commas. An absolute path, a path or symlink leading outside the checkout, a directory with no `go.mod`, tags set without `sseFixture`, or any other tags fail that job, and the `validate` and `engines-floor` jobs are skipped. Every shard of `validate` and `engines-floor` then sets up Go with `actions/setup-go` from the module's `go.mod`, caching modules by its `go.sum` when it has one, runs `go build -tags <tags> -o $RUNNER_TEMP/sse-fixture .` in the module directory, and sets `SSE_FIXTURE` to the binary's path for the steps after it, the tests among them. A build that fails fails the job. The steps need no root, so they run the same on a self-hosted runner.

In a TypeScript package with a knip configuration, `ts-ci.yaml` also runs [knip](https://knip.dev) for four checks that are not dead code. They are import cycles, imports of packages that `package.json` does not declare, binaries that `package.json` does not declare, and the same value exported twice. Unused code is left to the dead-code check. A cycle fails only when the configuration sets `"rules": { "cycles": "error" }`.

## The dead-code check

`deadset-ci.yaml` runs [deadset](https://github.com/cplieger/deadset) at the repository root, and once in each nested Go module folder. The root run covers the Go and TypeScript that deadset finds there, with deadset-go and deadset-ts, so deadset can match an edge that crosses from one language to the other. deadset-go stops at a nested module's `go.mod`, so each nested module gets its own run for its Go. deadset-ts at the root already reads every TypeScript project below it, nested modules included, so a nested run leaves TypeScript out.

In a repository with no `go.mod` at the root, the root run is the only one. deadset-go, run in a folder that no `go.mod` governs, analyzes every module below it in one report, so a reference from one module to another counts. Before the analysis, the workflow downloads each of those modules' dependencies.

A run reads its settings from `deadset.json` at its root. Every key that file sets wins, except `reporters.formats`: the workflow always asks for text and SARIF. When the file leaves `target.kind` out, it is `application` if the folder has a `Dockerfile` and `library` otherwise. deadset then reports no unused export from a library's published API, because callers outside the repository may use it.

The languages are the `analysis.languages` of `deadset.json`. When the file names none, a nested module's run takes Go alone, and the root run lets deadset detect them from file names, as its [commands page](https://github.com/cplieger/deadset/blob/HEAD/docs/commands.md#how-languages-are-detected) describes, so TypeScript test fixtures count too. A repository that holds fixtures in a language it does not ship lists its own languages. The workflow first asks deadset which languages and analyzers the run will use, with `deadset print-languages`. The check passes and analyzes nothing only when deadset finds no language in scope at the root; any other failure of `print-languages` fails the check. The workflow then installs only the analyzers deadset names, and fails before the analysis when a language's setup cannot be derived:

- The workflow installs deadset-go and deadset-ts only, so a `providers.analyzers` that names another analyzer fails.
- TypeScript needs a committed `package-lock.json` when it has a `package.json`. Both count only outside `node_modules`, `testdata`, `vendor` and hidden folders. Each folder that holds a lockfile is installed with `npm ci`. JavaScript with no `package.json`, such as a script run with `node`, installs nothing.

deadset reads some languages itself, such as Protocol Buffers, so a root holding only `.proto` files needs no analyzer: the workflow installs none and runs the analysis.

When the analyzer of a detected language finds no program, for example in a `tsconfig.json` with no inputs, deadset leaves that language out and reports the rest. When `analysis.languages` names the language, or the analyzer cannot read its configuration, the check fails.

Any finding at `deny` severity fails the check. So does a run that gives no answer, such as a missing or refused analyzer, and a run that ends without writing its SARIF report. To keep a symbol, put a `deadset:ignore` directive with its code and a reason on the line above it. A `deadset.json`, `deadset-ignore.json`, `deadset-baseline.json` or `deadset-edges.json` in an npm project folder below the root is never read, so the check fails and names it. Move it to the root and make its paths relative to the root. deadset-go never analyzes the Go source an npm package ships under `node_modules`.

Each run also writes SARIF and uploads it to code scanning, under the category `deadset`, or `deadset/<folder>` for a nested module. Each analyzer's findings stay a separate analysis inside that category. The upload needs `security-events: write`, which the synced `ci.yml` grants. It is skipped in private repositories, and a failed upload never fails the check.

In `cplieger/ci` itself, a `deadset-canary` job runs the same workflow with the pinned deadset, deadset-go and deadset-ts over seven public repositories at fixed commits, and ignores their findings. A version bump that makes deadset refuse a run or give no answer fails that job before a release carries it.

## The performance gate

`perf-ci.yaml` measures a web app in real browsers and holds each measured cell to its budget. A repository enrols by committing `tests/perf/plan.json`, and the repository owns everything it measures:

- `plan.json` holds `node`, the npm package folder whose lockfile pins Playwright, and `sets`. Each set, such as `pr` and `full`, has `shards`, the most measure jobs it splits into, and `cells`, each a `scenario`, `scale`, `engine` and `width` with the `seconds` it takes to measure. A cell may list `windows`, a non-empty list of distinct window names, to measure only those windows; a cell without it measures every window. A set or cell that is not an object, and a line break in `node` or in a cell's field, fail the plan, because those values reach the job's outputs and shell. Jobs get the longest cells first, each onto the shard with the least work so far.
- `tests/perf/build.sh <dir>` writes the build into the folder. It runs once, with Go set up from `go.mod` when the root has one and Node 26.
- `tests/perf/run.sh <cells.json> <out>` measures the listed cells against the build, whose folder `PERF_BUILD` names, and writes `<out>/results.json`. Each measured cell is the plan's four fields plus a `window`, a `metric` such as `cpu_ms` or `reads:/api/chats`, a `kind` and its `reps`. The kind is `time` (judged against its budget), `server_cpu` (judged against its target), `count` (must equal its budget) or `report` (never gated). Each measure job is a call of `perf-measure.yaml`, which installs Chromium and WebKit and stamps the runner label and the CPU model into the file itself.
- `tests/perf/budgets.json` holds `schema` 1, the `runner` the budgets were calibrated on, a `headroom` above 0 and a `floor` of 0 or more per metric family, and `budgets`. Each entry names its cell by the six fields and carries a `tier`, a `source` (the calibration run's URL) and `rows`, a non-empty list. A `gated` entry's `budget` is `max(floor, baseline × headroom)`, from its own `headroom` when it has one, which must also be above 0. A server CPU entry's budget is its `target`. An `exact` entry's budget is its baseline. A `reported` entry gates nothing.

The `compare` job judges each cell on the median of its three reps. A gated cell over its budget does not fail there: the `remeasure` jobs measure it again on new virtual machines, and the `verdict` job fails it only when the median of all six reps is over its budget. An exact count that differs from its budget fails at once. A cell whose median is under its baseline divided by its headroom gets a notice that its budget can come down, and a cell with no entry is reported. The job reads `plan.json` too: a gated or exact entry whose cell and window the run planned but no shard measured fails, and so does one whose cell and window neither the `pr` nor the `full` set lists, the two sets a workflow runs, unless a `retired` entry names it. Results from a runner other than the file's `runner` report every metric and gate none. A budget file that breaks the rule above fails, and so does a number a float cannot hold in any file the gate reads, such as `NaN`, `Infinity`, `1e999` or a 400-digit integer. A file that is not a JSON object, or a budget entry or `retired` item that is not one, fails with an error line naming it, and the gate then judges no cell. The run summary lists every measured cell.

Every budget a pull request changes must come from a signed calibration. An entry is changed when it is new or its baseline, budget, tier, headroom or source differs from the base branch's file, and every entry is changed when the file's `runner`, `headroom` or `floor` differs. Its `source` names a run of `perf-calibrate.yaml` in cplieger/ci, and `tests/perf/calibrations/` holds that run's `<run id>.json` and `<run id>.sigstore.json`. The check fails when the bundle does not verify as signed keyless by `perf-calibrate.yaml` on `refs/heads/main`. It also fails when the file was made for another repository or runner, measured a commit the head does not contain, or holds another baseline for the cell. An entry may raise its baseline only with an `accepted` reason, and after a `headroom` or `floor` edit it needs one to raise its budget too, whatever the calibration file holds. A server CPU entry needs one to raise its target. A gated or exact entry leaves only through a `retired` entry naming its cell and a `reason`. A file in `calibrations/` that no entry names fails too.

`perf-calibrate.yaml` is started by hand with a `repo`, a `ref`, a `set` (default `pr`), an `only` list of scenarios and a number of `runs` (default 10), and measures public repositories only. It uploads a `budgets-proposed` artifact for 90 days, holding `budgets.proposed.json` and the same bytes as `<run id>.json` with its `<run id>.sigstore.json` bundle, the two files to check in. Only ten runs or more decide a tier. A count is exact when every rep of every run agrees. A time takes each run in turn as a pull request against the median of the other runs, at the metric's headroom: a cell whose median of six passes stays gated, and one that trips gets the smallest 0.05 step of headroom at which none does, up to 2.0 for CPU and 1.5 for heap and RSS, past which it is reported. `whole_pr` lists the runs that would have needed a re-measure, and the cells widened or demoted. A run of fewer than ten re-measures baselines: its entries keep the base file's tier and headroom, a new entry from it is `reported`, and a gated cell whose spread trips the second stage at its headroom fails the check, which asks for a ten-run calibration.

`weekly-perf.yaml` measures the `full` set of every public cplieger repository that carries `tests/perf/plan.json`, on its default branch, through the same gate. Each cell's median goes to `perf/` on the repository's `benchmarks` branch, and a chart's alert never fails the run.

## The release workflow

`release.yaml` reads the release type from the repository root. A `Dockerfile` wins over `jsr.json`, and `jsr.json` wins over `go.mod`. It computes the next version with git-cliff from conventional commits and the repository's `cliff.toml`. A push that touches only paths such as Markdown, tests, lockfiles or `.github/` publishes nothing. A file under one of those patterns still ships when a non-test `//go:embed` names it, such as a manual a binary prints. A change to it alone releases, its commit sets the version bump, and its line appears in the release notes. An eligible Go module in a subfolder gets its own version and its own `<folder>/vX.Y.Z` tag. Its module path must start with a domain name, its folder must hold tracked Go files and sit outside `internal/`, and it must not contain or sit inside another module's folder.

A repository whose root has no `Dockerfile`, `jsr.json` or `go.mod` releases only its nested Go modules. Its root gets no version, tag, GitHub Release or completion status. A first-level folder with a `jsr.json` is a TypeScript subpackage of the root and shares the root's version, so in such a repository a change to one fails the run.

A nested Go module whose folder holds a tracked `web/jsr.json` and `web/package.json` has a TypeScript half at `<folder>/web`, which publishes at the module's version. The tag `<folder>/vX.Y.Z` publishes `X.Y.Z` to npm and then JSR, and `<folder>/vX.Y.Z-dev.N` publishes to npm under the `dev` dist-tag. The half publishes after the module's tag exists, and only when a file it ships changed since the module's previous release on that branch, and always at the module's first release. Changes to its `package.json` that touch only `devDependencies` or `overrides` do not count, as for a root subpackage. Give `web/` its own `go.mod`, such as `module web-ignore`, so Go tooling skips the folder.

A nested module's first version is `v1.0.0`, and `v1.0.0-dev.1` on `dev`. To start elsewhere, commit `<folder>/.first-version` holding one line, such as `v1.5.0`. The file is read only while the module has no stable tag, and an edit to it counts as a change to the module, so delete it after the first stable release. Before it tags a module with a TypeScript half, the run reads the package from npm. It refuses the version when npm already serves it from another commit, or when the version does not rank above every version npm holds from a commit outside this repository, such as the package's releases from before it moved here. The error names the `.first-version` that would pass.

A TypeScript subpackage or module half whose `package.json` sets `"private": true` publishes nothing. Its run does an `npm publish --dry-run` instead, plus a `jsr publish --dry-run` on `main`, and skips the read-back from the registries.

Before it tags a release or pushes an image, the workflow checks the root `go.mod` module path. A library's path must be `github.com/<owner>/<repo>`, with a `/vN` suffix from major version 2 on. An image repository's path must be the plain `github.com/<owner>/<repo>` at every major version, because nothing imports an app. A repository with no root `go.mod` skips the check.

Before it tags a Go library, the run compares the root module's exported API with the newest stable tag using [gorelease](https://pkg.go.dev/golang.org/x/exp/cmd/gorelease). It fails when the change is incompatible but the version is not a new major. The check runs on both channels against the next stable version. It skips a root `package main`, a first release and a major bump.

When gorelease cannot install, run or load the packages, the run warns and lets the release through. It fails when gorelease rejects its own arguments. The run summary shows the gorelease report.

To ship a decided incompatible change in a minor release, commit `api-accept.txt` at the repository root. Each line names one change as `<package import path>: <line from the gorelease report>`. Copy the line from under `## incompatible changes`, below that package's `# <package import path>` heading. Lines starting with `#` and blank lines are ignored. An entry must match a whole report line of the same package.

When gorelease cannot load the new version's packages, the run lets the release through as described above and does not read the file. Otherwise the file lets gorelease's rejection pass only when all of these hold:

- Every incompatible change in the report has an entry.
- No package has a load error.
- gorelease reports no diagnostic and no reason other than the incompatible changes.
- The version raises the minor version over the newest stable tag.
- The Go module proxy does not already list the version.
- No dependency requires a higher version of the module.

gorelease's verdict on incompatible changes hides those last three checks, so the run makes them itself. When it cannot list the published versions or the module graph, it keeps the release failed. Like gorelease, the run reads the module graph as a module that depends on this one sees it. The repository's own `replace` and `exclude` directives therefore do not hide a dependency that requires a higher version.

The run warns about each entry that matches no incompatible change or repeats an earlier entry. A line that is not in the `<package>: <change>` form fails the release. The run summary lists the accepted, unaccepted and unmatched entries. Delete the file once a stable tag contains the change, or the next releases warn about every entry. Committing the file starts a release like any other change, so adding it reruns the check on the change it accepts.

The branch picks the channel. A push to `dev` publishes the dev channel, with `vX.Y.Z-dev.N` tags, `:dev` images on GitHub Container Registry, the npm `dev` dist-tag and no GitHub Release. A push to `main` publishes the stable channel, with a `vX.Y.Z` tag, GitHub Container Registry and Docker Hub images, npm and JSR packages, and a GitHub Release. A run on any other branch, a tag or a pull request fails with an error and publishes nothing.

Runs on one branch queue, and a newer push replaces a run still waiting, so the run on the newest head always comes last. Once a push that edits workflow files lands past a run's commit, GitHub refuses that run's tag create. The run then hands its version off: it ends with a warning, and the run on the newest head releases every commit since the last tag under one version. The root TypeScript package checks before it reaches npm, which keeps every version it receives, and hands off when the branch has moved and its version has no tag at the run's commit. A subpackage or a lane's TypeScript half hands off when its version has no tag there and the branch has moved. A refused tag create while the run is still the branch head stays an error.

A dev build is numbered as the next promotion, so a library's dev run whose code is the same as its highest stable release publishes nothing. Otherwise that pre-release would rank above the stable release and move every consumer's `dev` onto it. This covers a Go or TypeScript root together with the TypeScript subpackages that share its version, and each nested Go module. A library whose dev pre-releases already rank above its stable release still builds, because only a newer pre-release brings that stable release's code to the consumers on them. An image repository still builds, because a promotion re-tags that build.

`release.yaml` publishes only from a public, non-fork repository whose default branch is `dev`, which follows [the two-branch release model](#the-two-branch-release-model). For any other caller its first job fails with an error, before anything is built or published. The sync gives a repository with only `main` no release workflow, and such a repository publishes, if at all, from its own workflow.

`docker-release.yaml` is called by `release.yaml` and never directly. Its first job refuses the same callers, in a repair as in a release. Its work splits by channel.

On the dev channel it builds the image on native `amd64` and `arm64` runners and pushes it to GitHub Container Registry. It signs the image with cosign, attaches an SBOM and runs a Trivy scan. A repository with a root `grafana-dashboard.json` also gets the dashboard pushed as the OCI artifact `ghcr.io/<owner>/<image>/dashboard`, and each root `grafana-dashboard-<suffix>.json` as `ghcr.io/<owner>/<image>/dashboard-<suffix>`, all at the release's version. A suffix is lowercase letters and digits in runs joined by single hyphens, such as `messages` or `logs-2`. The `repo` job and the release refuse any other `grafana-dashboard-*.json` at the root by name, because its package name could be invalid. GitHub makes a new package private on its first publish, so the release that first pushes a dashboard package fails its read-back from the registry until you make that package public and rerun the failed job.

On the stable channel it re-tags the image the dev channel built for that commit as `vX.Y.Z`, `vX.Y`, `vX` and `latest`. It copies the image to Docker Hub with its signatures and creates the GitHub Release with its assets, described below. When it promotes a build, the Release's SBOM is the one that build signed into the image, read only once its signature checks out. When no dev build matches, it builds from source and says so in the run summary. It also writes the Docker Hub overview page from the README.

The app image it builds, on either channel, then runs the `docker` job's two image tests in an `image-test` job, against the `amd64` digest the build pushed and before anything is tagged. A failure, or a run cancelled before the tests pass, leaves that digest without a tag. A rebuild-only range relies on this: its pull request changes no file, so the `docker` job skipped it, and the base packages it refreshes are tested only here. The job has read access to packages only, so the repository's test scripts never run beside the build's write token. The release does not test the runner images described below. On a pull request, the `docker` job runs the repository's integration tests against them when it has some, as [the CI entry point](#the-ci-entry-point) describes.

A stable image release carries these GitHub Release assets:

- `sbom.spdx.json`, the image's SBOM;
- `grafana-dashboard.json` and each `grafana-dashboard-<suffix>.json` the release commit holds at the repository root;
- `openapi.json`, the release commit's `docs/openapi.json`, when it holds one;
- the repository's client as binaries for Linux, macOS and Windows on `amd64` and `arm64`, named `<name>-<goos>-<goarch>` with `.exe` on Windows, when `release.yaml`'s policy step names a client for the repository. `scripts/release-assets.sh build` compiles them from the release commit with `CGO_ENABLED=0`, `-trimpath` and `-ldflags "-s -w -X main.version=<tag>"`, using the Go version the module's `go.mod` asks for.

The SBOM, each dashboard, the API document and each binary have a cosign bundle, `<file>.sigstore.json`, signed by `docker-release.yaml`, and all but the SBOM also come with a `.sha256` checksum. So you can verify an asset without pulling the image. The run reads the Release back and fails if an asset is missing. A repository with no dashboard, API document or client gets the SBOM alone. When a stable run completes an earlier stable tag whose Release is missing, it creates that Release with the same assets: the SBOM attested to the tag's published image, and the files from the tag's own commit. It publishes nothing if one cannot be made. Before creating either Release, `scripts/release-assets.sh cleanup-drafts` deletes any draft Release of its tag, the kind an asset upload that died leaves behind.

A repository can publish more images on the same version line. Each `images/<name>/Dockerfile` is a runner image in the package `ghcr.io/<owner>/<image>-runner`, built with the repository root as its context, where `<name>` is 1 to 32 lowercase letters and digits. The dev channel tags it `<name>-vX.Y.Z-dev.N`, `<name>-dev` and `<name>-sha-<commit>`. The stable channel tags it `<name>-vX.Y.Z`, `<name>` and, for a build, `<name>-sha-<commit>`. A renumber run re-tags each runner image's build of the commit as `<name>-vX.Y.Z-dev.N` beside the app image, and refuses before any tag when one of them is missing. Like the app image, each runner image is built on native `amd64` and `arm64` runners, signed with cosign by `docker-release.yaml`, and given an attested SBOM and a Trivy scan, whose findings go to the Security tab under `trivy-image-runner-<name>`. Its licence label comes from `runner_image_licenses` in `release.yaml`'s policy step, or else from the app image's.

A runner image can build on another one by naming its moving tag as a `FROM` image, a `COPY --from=` or the `from=` of a `RUN --mount`, as in `FROM ghcr.io/<owner>/<image>-runner:base-dev`. The release builds that image first and swaps those three forms for the digest it just pushed, so an image never builds on an older copy of another. The build rewrites no other mention, so a moving tag named anywhere else, such as in a `RUN` command, an `ENV` or a `LABEL`, fails the release. Any other reference to the package, such as a version tag, a digest or the image itself, fails the release too, and so does a cycle.

A stable promotion re-tags the runner images that the dev channel built for the promoted commit when every one of them was signed and attested by that build. Otherwise all of them build from source. Each runner image is pushed under `<name>-sha-<commit>` only, then scanned, signed and attested. `finalize` writes every runner image's version tag and then every channel tag right after it moves the app image's channel tags. It starts only once every runner image is signed and the app image passed `image-test`, and the write follows each check that can refuse the release. So a failed runner image, a failed image test or a refused release moves no runner tag and leaves the version untagged, and the next run publishes it. A failure after the app image's tags moved is completed by a rerun of `finalize`, as for the app image. They get no Docker Hub copy and no Release asset. The rebuild-only comparison reads the app image only, so a rebuild-only range in a repository with runner images always publishes. The weekly `rebuild-stale.yaml` ages each runner image whose Dockerfile installs packages under `PKG_REFRESH`, by `<name>-dev` on `dev` and `<name>` on `main`, as it ages the app image, so a stale runner image rebuilds its channel even beside an app image that installs no packages. `ghcr-retention.yaml` keeps the newest ten dev builds of each runner image. GitHub makes a new package private on its first publish, so the owner makes the runner package public in its settings before anyone pulls it without logging in. A repository with no `images/<name>/Dockerfile` releases as before.

A job that runs a script or action from cplieger/ci first checks out cplieger/ci at the commit you pinned. The copy goes to `.cplieger-ci` beside your checkout and keeps no token on disk. So the commit you pin decides every line of cplieger/ci code the run executes. The `pr-policy` job of `ci.yaml` works the same way.

## The two-branch release model

In a repository whose default branch is `dev`, human work merges into `dev`, and `main` takes machine updates and promotions only. A promotion moves `main` to a tested `dev` commit, and `promote.yaml`, described below, is the one way to start it.

- A `dev` build is numbered above every stable release. Its version is at least the next minor above the highest stable tag, or the next major when its changes include a breaking one. Below 1.0.0, a breaking change takes the next minor instead.
- A commit on `main` that is not a promotion publishes the next patch and never more. Its image is built from source, and its notes open with "Built from `main` for dependency and system-package updates".
- A range whose only reason to release is a rebuild request from the rebuild job builds the `amd64` image first, without pushing it. When its packages equal those of the release it follows (the previous stable release on `main`, the newest `-dev.N` build on `dev`), the run publishes nothing and says so in a notice and its summary. Both images are scanned the same way, and the earlier one is first checked against its release's attestation. If that check, either scan or the comparison fails, the rebuild publishes.
- A repository's root and each nested Go module are separate lanes, each with its own versions. The release run at a promotion publishes a lane only when a file the lane ships changed since the lane's last stable tag. For an image, an empty rebuild commit merged into `main` itself since then also counts. A lane with no such change gets no tag, no Release and no stable registry tag.
- A lane whose shipped files the promotion itself changes publishes the next minor, or the next major when it carries a breaking change. Below 1.0.0, a breaking promotion takes the next minor. Its image is the `dev` image its promotion commit names in a `Promoted-Digest:` trailer, after a check that the digest is in the repository's own package. Its notes open with "Promoted from" and the `dev` version. A lane whose only unreleased shipped change came from a `main` commit publishes that commit's patch.
- When another commit reaches `main` before a promotion has released, that commit builds from source and publishes the promotion's version.
- Before a promotion's first tag or registry write, the run waits for every `dev` release run that started earlier. If `dev` then holds newer work and no pre-release above the version, the run dispatches `release.yaml` on `dev` with `mode=renumber` and waits for it. A renumber run tags the existing `dev` build under a new pre-release version and builds nothing. The caller template grants `actions: write` for this dispatch.
- A stable lane is complete once its GitHub Release exists and its published artifacts read back from the registries. npm scans each new version for malware before it serves it. The read-back therefore waits up to 20 minutes for npm and up to 10 minutes for every other registry. The run then sets a `release/complete/<tag>` commit status. Every stable run first completes each lane's highest stable tag that lacks this status, at the tag's own commit. For a nested module, that includes publishing a TypeScript half its tag's run did not publish.
- The wait for newer `dev` work and the renumber cover a nested module's TypeScript half as they cover a root subpackage: before it publishes, npm must serve a `dev` build of the half's newest change that ranks above the module's version.

`scripts/render-notes.sh` writes the notes of each released lane from the lane's previous stable tag to the release commit. After the opening line come breaking changes, then Security, Added, Fixed, Performance and Changed, then a compare link to the previous version. Commits scoped `deps` or `devdeps`, which Renovate writes, stay out of these lists but still count for the version.

A collapsed Dependencies block follows. It lists what changed in `go.mod`, `package-lock.json`, `uv.lock`, Dockerfile `FROM` lines and pinned versions, and marks updates from a Renovate security pull request. An image release ends with a System packages block from the two signed SBOMs.

`promote.yaml` in this repository promotes a chosen `dev` commit to `main`, on demand only. Its inputs are `repo`, `target`, `dry_run` and `accept_vulnerabilities`, and `target` defaults to the head of `dev`. It refuses the promotion unless all five checks pass:

- The commit's root pins no first-party dependency at a `-dev.` version, in its own manifests or its shipped pin files.
- Each image lane still has a signed `dev` image on GitHub Container Registry, built from that commit or from an ancestor with no shipped change since.
- Every file that changed on `main` since the branches split is a dependency file or a synced file. The commit has each dependency at the same version, a newer one or none, and each synced file equal to `main`'s copy or the current one here.
- The commit's image publishes every platform the image of `main` publishes, and has no fixable `HIGH` or `CRITICAL` finding, on any platform, that the image of `main` lacks. A finding whose ID is listed in `accept_vulnerabilities` passes this check: use it when no rebuild here can fix the finding, such as a package inside a base image, and the run summary names each accepted ID.
- The commit's tree differs from `main`'s.

A nested Go module whose own manifests (its `go.mod`, and its TypeScript half's `package.json` and `jsr.json`) pin a first-party dependency at a `-dev.` version does not refuse the promotion. It is held back: the promotion moves `main` and the other lanes publish as planned, but the stable run publishes nothing of that module. The preview names it under "held back", the checks' summary names its pins, and the stable run's log names the lane. A held promotion is not the module's pending promotion, so a later commit on `main` does not publish it while its tree still pins the dev version. The module publishes from the first stable run whose tree pins it only at stable versions, which is normally the next promotion. A library whose modules require each other promotes in two passes this way: the first publishes the modules with no dev pin, then each held module moves to those stable versions on `dev`, and the second promotion publishes it. `scripts/purity.py` holds the rule that `promote.py` and the stable run both apply.

A promotion that changes no path any lane ships still moves `main`. Its preview names the version each lane will publish, or says the lane has no release. The preview starts once every release run of `main`'s head has finished, so it counts the tags those runs create. The promotion waits up to 45 minutes for them, then stops and asks for a rerun. On `main`, an empty rebuild commit counts as a change only when it was merged into `main` itself, not when a promotion brings in one from `dev`.

`promote.yaml` then writes a promotion commit whose tree is the `dev` commit's and whose parents are `main` and that commit. For an image, it next tags the promoted `dev` image `promoted-<promotion commit>` on GitHub Container Registry, even when no lane will publish, and the cleanup of aged `dev` images never deletes an image with that tag. `main` moves to the promotion commit only after that tag exists and only if `main` has not moved since the checks. `dev` is never written. A dry run stops after the checks.

Each run is named `Promote <repo>`, with `(dry run)` after a dry run. Runs for one repository run one at a time, and up to 100 can wait for their turn without any being cancelled. Runs for different repositories run in parallel.

## The security workflows

- `codeql.yaml` runs CodeQL with the `security-extended` and `security-and-quality` query suites on public repositories. It detects the languages itself.
- `security-scan.yaml` runs Trivy filesystem, misconfiguration and image scans for `HIGH` and `CRITICAL` findings, plus a gitleaks scan of the full git history. Every one of them is advisory. The findings go to the Security tab and never fail the run.
- In a two-branch repository, a run of `security-scan.yaml` on `main` that is not a pull request builds nothing. It scans the published `:latest` image on every platform, the checkout's lockfiles and `go.mod` files, and each Go module with `govulncheck`. It writes the findings to a `security-main` artifact and the run summary.
- Components the image builds from source are listed as not covered, because no scanner has been shown to match their advisories. The list comes from the published image's signed SBOM, which names every CycloneDX fragment the image ships, a fragment a build script writes included. The Dockerfile's fragments, followed through its build stages, and a list of names kept per fragment path are added to it.
- The run fails when a report is missing, when the signed SBOM cannot be verified or read, or when a fragment in the image has no name any of those ways, so a partial scan never reads as clean.
- The `security-main` artifact holds one `security-main.json` record, schema 1. Its fields are `schema`, `repo`, `commit`, `image`, `findings`, `not_covered`, `complete` and `errors`.
  - `image` is null, or the image's `ref`, its `digest` and a digest per platform.
  - Each finding has an `id`, a `package`, the `installed` and `fixed` versions, a `severity`, a `class`, and the `targets`, `platforms` and `sources` it was found in. `fixed` is null when no fix exists, and `severity` is null for a govulncheck finding.
  - The `class` is `os` for an image OS package, `stdlib` for the Go standard library, `manifest` for a shipped manifest or a package inside the image, and `lockfile` for a lockfile entry.
- Trivy reports only HIGH and CRITICAL findings. govulncheck reports only the vulnerabilities whose code the module calls.

## Workflows for this repository only

Every other file in `.github/workflows/` runs inside cplieger/ci and is not meant to be called. These workflows sync the configs, cut and move release tags, run the daily settings audit, and run the scheduled mutation, fuzz, benchmark, performance, link and security jobs. `perf-calibrate.yaml` calibrates a repository's performance budgets, as [the performance gate](#the-performance-gate) describes. Others rebuild images older than seven days by default, promote a `dev` commit to `main` in a two-branch repository, delete aged dev images from GitHub Container Registry, and run this repository's own CI.

In a two-branch repository, the rebuild job reads when the published `:latest` and `:dev` images were built. For each one older than the limit, it opens a pull request into `main` or `dev`, unless a rebuild request merged into that branch within the limit. A rebuild that published nothing is therefore not requested again the next day. The daily security job runs each two-branch repository's security workflow on `dev` and again on `main`.

`renovate-heartbeat.yaml` runs daily at 07:41 UTC, and on demand with an `hours` input. It asks GitHub search for pull requests that the resident Renovate opened, from a `renovate/` branch as the `tribble-trouble` GitHub App, in any `cplieger` repository in the last 48 hours. The sync and rebuild pull requests that this repository's workflows open as the same App do not count. When it finds none, it opens or updates one `Renovate stopped opening pull requests` issue in docker-renovate-scheduler, labelled `renovate-heartbeat` and assigned to the owner. The first run that finds a pull request closes the issue. A search that fails, or that GitHub marks incomplete and that finds nothing, fails the run instead of deciding. The check sees the deployment stop for any reason, but not a fault that only another authentication mode meets, which the image smoke test covers.

The daily settings audit holds a two-branch repository to squash merges titled by the pull request title, and to the two rulesets in `configs/rulesets/`. It also requires the synced `renovate.json` and a `release/complete/<tag>` status on each lane's highest stable tag.

On its schedule and when started by hand, the audit files its findings as issues. Each public repository it grades that has issues turned on keeps one `Repository audit findings` issue, labelled `repo-audit`. The findings of any other repository stay in the run summary. The issue lists the repository's HARD findings and warnings. It is updated in place on each run and closed once the repository audits clean.

A repository created less than 24 hours ago is graded but gets no issue yet. When a read for a repository fails, its issue is left as it is for that run. A public repository outside `SINGLE_MAIN_REPOS` whose default branch is `main` and which calls `release.yaml` is a HARD finding, because that workflow refuses it. One that publishes from its own `publish.yaml` is a warning until it is added to `SINGLE_MAIN_REPOS`.

`community-data-refresh.yaml` runs on the 3rd of each month at 08:17 UTC, and on demand. It opens the pull requests that refresh the community data some repositories ship, such as langtag's CLDR tables. The repositories, their base branches and the paths each may change are listed in `REPOS` in `scripts/community_data_refresh.py`. A run started by hand can name repositories in `only`.

Each listed repository runs its own refresh in its own `community-data-refresh.yaml`, on its base branch, on the 3rd of each month at 05:17 UTC. That workflow holds no secret and uploads a `community-data-refresh` artifact, the proposal:

- `proposal.json` holds `{"changes": [...]}`, the paths the refresh changed, which is empty when there is nothing to refresh.
- `files/<path>` holds the new content of each listed path, and nothing else.
- `title` holds a one-line pull request title and `body.md` its body, when a path changed.

This workflow runs none of the repository's code. It reads the newest completed refresh run on the base branch, fails when that run failed, and refuses a proposal that lists a path outside the row's paths, holds a link or an unlisted file, or exceeds the size and text limits. When the proposal changes anything, it opens or updates one `community-data-refresh` pull request against the base branch, with an App token scoped to that repository. The pull request carries one commit on the commit the refresh ran on, changing only the paths the proposal lists. Base-branch commits made since then to other paths are expected, and the pull request's merge takes them in. The run fails without writing in two cases. First, the commit the refresh ran on is no longer in the base branch's history, because the branch was rewritten. Second, a path the proposal lists differs between that commit and the base branch's tip, so the proposal would overwrite a later edit; the error names each such path and both of its git object ids. In either case run the repository's refresh again, then this workflow, or wait for the next scheduled refresh. While the pull request holds a commit someone else pushed, it is left alone: the run proposes nothing and shows a warning on its summary page, so merge or close that pull request to let the next refresh through. Nothing merges it: it waits for `ci / validate` and a human merge.

`release-maintenance.yaml` runs every hour for two-branch repositories only. It merges a Renovate security pull request on `dev` or `main` when `ci / validate` is green and the pull request carries a patch, minor, digest or pin label.

For a fixable finding of the daily scan of `main`, it asks Renovate to run the weekly `main` group early through the Dependency Dashboard. It does so when the group updates the package or, for an image that installs no packages, the base image its final stage is built on. The dashboard lists a group's packages only when the group holds two or more, so a finding against a group with no list is reported in the issue instead. It acts only on a complete scan that started in the last 36 hours.

For an OS package of an image whose final stage installs packages, it opens a rebuild pull request into `main` instead. The rebuild refreshes those packages only when an install runs after an `ARG PKG_REFRESH` line, in the same stage or in a stage it is built from. Otherwise the finding is listed in the issue.

It also keeps one issue per repository, labelled `release-blocked`, and closes it once every section is clear. The title names the sections the issue holds, such as `Vulnerability fix has no automatic route`, so a finding that blocks no release does not read as a blocked one. The issue lists the Saturday update when it has not shipped by 12:00 UTC. It lists any security, expedited or rebuild pull request into `main` that has not shipped within three hours. An expedited one is the weekly `main` group opened early, or any other Renovate update into `main`, such as an update of the `ghcr.io/actions/actions-runner` base image. It also lists every fixable finding with no automatic route, and a missing, older or incomplete scan. When a read fails, the issue keeps the sections that read would have checked as they were, and the issue is not closed that hour. It also stays open in an hour when a planned merge, rebuild or dashboard tick did not happen, for example because the dashboard changed after it was read.

## The scheduled runs

The weekly workflows run each repository's mutation tests, fuzz targets, benchmarks, browser performance runs and link checks here in cplieger/ci, so one place holds the schedule, the matrix and its `max-parallel` cap. The performance run goes on Mondays, Stryker on Saturdays, gremlins on Sundays, benchmarks on Tuesdays, fuzzing on Wednesdays and the link check on Thursdays, all at 22:00 UTC.

They take only repositories that are public, not archived and not forks, because anyone signed in to GitHub can read this repository's run logs and artifacts. A private repository that wants these runs runs them in its own CI. A job that runs a repository's code clones it anonymously and references no secret. The jobs that publish a badge, update a tracker issue or file a finding run no repository code. They take each repository from their own matrix and download only the artifacts that repository's run entries uploaded, by exact name.

The two mutation runs test each repository in its own call of a reusable workflow, `mutation-stryker-repo.yaml` or `mutation-gremlins-repo.yaml`, so a repository that fails ends only its own call and the others run on. Each takes a `repository` input and, to test one target alone, a `dir` (Stryker) or `module` (gremlins) input; a one-target call publishes no badge or tracker update, because both describe the whole repository. A whole-repository call needs `CI_SCHEDULE`, which only the badge and tracker jobs read, and those jobs fail when it is missing; a one-target call needs none. Each call ends with a `result` job that writes one record: every package directory or Go module it found, which of them it tested, and for each one tested, refused, failed, not run or opted out, with the reason. A target counts as tested only when its merged result holds at least one mutant a test judged (killed, survived, timed out or not covered), counted from the merged report itself; a target whose merged result is missing, unreadable or empty is not run. For gremlins the count is the fewest over the week's attempts. The call passes when it tested at least one target, no job failed or was cancelled, and nothing it found was refused, failed or left unrun; otherwise its `result` job fails. A one-target call skips the badge and tracker jobs and still passes on the same rule. A call whose every target opts out (`stryker.weekly.json`) passes with a notice. The weekly run's `summary` job reads each record on its own, lists every repository's outcome and reason in the run summary, and fails the run unless every call passed or opted out; a call that left no readable record fails it too, named by repository. A matrix job's result covers all its jobs, so one failed shard marks every target of that call failed. A Stryker package directory with no `@stryker-mutator/core` devDependency is not run, which fails its call. A package directory or Go module whose name holds a character other than a letter, a digit, `.`, `_`, `-` or a directory's `/` is refused in both runs: it is not tested, it is named with an error, its call fails, and every other target of the call is still tested and published. A repository whose listing could not be read runs anyway, so its own call fails if it cannot be tested. A run that finds nothing to test fails.

`weekly-stryker.yaml` mutation-tests each TypeScript package directory, the root or a subdirectory such as `static-src/`, that commits a `stryker.config.json`. The directory also needs the devDependencies its config names: `@stryker-mutator/core` and `@stryker-mutator/vitest-runner`, plus `@stryker-mutator/typescript-checker` when it sets `checkers`. When it declares a `test:mutation` script, the run calls that script instead of `stryker run`. A directory without `@stryker-mutator/core` is not run, and one missing another devDependency its config names fails; either fails its call. A directory that commits `stryker.weekly.json` as `{"weekly": false}` is skipped on the schedule only, and a run started by hand still tests it.

Each directory runs in full once a week. A `plan` job first runs Stryker until its mutation testing plan is ready, which gives each mutant's lines and the time of the tests that cover it. A directory whose run would pass its band (below) is split into shards, priced by each file's measured cost in the last run where there is one, and from the plan job's estimate otherwise (below). A file too large for one shard is split into line ranges (`file.ts:first-last`, Stryker's `mutate` range), cut only where no mutant spans the cut, so each mutant is in exactly one range; a range is priced from the last run's measure of the same lines while the file is unchanged (its git blob), and at three times the plan job's estimate, as for a file no run has measured, once it changes. Stryker runs a mutant only together with every mutant nested inside it, so such a nest is never cut apart: a file or range is cut down to nests until each piece fits a shard. A directory takes at most 16 shards to bring its shards into their band, and its merge job's summary says when that count leaves a shard past the band's top; it takes more, up to GitHub's limit of 256 jobs in one matrix, where the bound on every job (below) needs them. A call whose directories need more than 256 jobs together fails, and so does a repository with more than 16 package directories. A directory holding more than one Stryker config runs once. A `merge` job joins the shards, and the ranges of a split file, into the one report the badge and tracker read, so a sharded run reads as an unsharded one. The plan pass mutates the whole file, so its list of mutants decides which mutants a split file has and which of them a `// Stryker disable` comment ignores: a ranged run can miss a comment outside its range, so the merge gives each mutant the plan pass's ignored status. Each shard of a split file also passes the first two characters of every `disable` or `restore` comment that is not `next-line` as a range of its own, so Stryker reads the comment and mutates nothing there. A split file whose shards report a mutant outside their ranges, the same mutant twice, a different count than the plan pass gave, a mutant the plan pass did not find, none for a mutant it found, or an ignored mutant the plan pass runs publishes nothing. A file of more than 100 such comments, one not tracked in git, or whose plan pass gave no mutant list, runs whole. A shard that fails or runs out of time publishes nothing for its directory that week. Each mutant's measured time is kept for the next run's plan while its file's git blob is unchanged; this run's measure replaces that mutant's last one, and a mutant no shard reached this week, such as one past a deadline, keeps its last measure.

Both mutation runs size their shards from the same bar: every job, on the slowest hosted runner, ends by 300 minutes, 60 under GitHub's 360-minute job limit, the run's measured time lands within 15% of its projection either way, and no shard runs more than 15% over its own projection. A shard under its projection only costs parallelism, so it is no fault. No single job is judged against its projection: a shard run in two or more attempts (gremlins) counts by its mean, and a run of one attempt per shard (Stryker) is judged by its total over its shards when it has two or more. Runners differ in speed by up to 1.9 times on identical work (`mutation_cost.SLOWDOWN`), and the setup slows with the rest of the job. So a shard is planned at most 300 minutes divided by 1.9 and by 1.15, about 137 minutes of setup and work together whatever the setup, and a shard whose mean runs 15% over its projection still ends by 300 minutes on the slowest runner. A Stryker directory with 31 minutes of setup gets at most about 106 minutes of work a shard, a gremlins module with 3 about 134. gremlins' record job measures the week's slowdown from its three attempts, keeps it in the cost history and warns when it passes 1.9. The cost history holds each mutant's measured seconds, keyed by its file's git blob and the mutant's own identity: its location and mutator for Stryker, its position and type for gremlins, which takes each mutant's mean over the attempts that measured it (gremlins' plan job records each Go file's blob as Stryker's does). A file, range or module costs the sum of its measured mutants' seconds, so a measure is never priced below what it took, plus three times the plan job's estimate (`mutation_cost.PRIOR_ERROR`) for each mutant with no measure at the file's current blob, such as one a deadline stopped its job before, or one in a file edited since. Only a value that is not a finite number of at least 0 is dropped. The margin of three is set well above what a shard has measured: per shard, Stryker run 43328238671's estimated work took at most 0.48 times its estimate, though one small file took 3.53 times its own. Every planned job, setup and work together, projects at most 300 minutes divided by 1.9, about 158 minutes, or the plan fails, naming the unit or the shard count, and that directory or repository is reported failed. The one exception is a unit run alone in its own shard whose estimate alone passes the bound, such as a Stryker nest no run has measured: the job's deadline stops it in time to save what it measured, and the run summary names it as unmeasured, running alone under the deadline. What it measured prices it the next week, and the mutants the deadline did not reach are named as not run, which fails that week's call. A nest still past the bound once fully measured fails its plan, naming its costliest measured mutant; testing one of its mutants at a time would need a Stryker ignore plugin in every shard's config, which the run does not add. A gremlins module or file of unknown cost also runs alone in a shard of its own. Both record jobs measure, per shard, how many times its estimate the estimated work took, from the units the run measured whole, one-job runs included, keep it in the cost history as `prior_error`, and warn when it passes 3.

Each Stryker shard restarts each test runner after 200 of its mutants (Stryker's `maxTestRunnerReuse`), so a test runner, and its Browser Mode Chromium where the directory uses one, lives at most 200 mutant runs, and runs Stryker below the runner's own priority (`nice -n 10`). Every shard logs a `runner-sample` line each minute with free memory, swap, free disk, memory pressure, the kernel's OOM-kill count and the Stryker main process, its Node workers and the Chromium processes, and uploads the series as `strykersamples-<key>-<n>` for 7 days. A shard that reaches its deadline gets SIGINT for its whole process group and SIGKILL 5 minutes later, and its error says which of the two ended it; a Stryker that ends on a signal before the deadline, such as an out-of-memory kill, is named by that signal instead.

Its score goes to the run summary and to a `mutation-ts.json` badge on the repository's `badges` branch, in the colour bands of the Go mutation badge. Stryker fails the entry when the score falls below the config's `thresholds.break`, which blocks no merge. Each repository keeps one `Stryker mutation testing tracker` issue, labelled `stryker-tracker`, with a 12-week score table and the surviving mutants grouped as Survived or NoCoverage. Notes written outside its marked blocks are kept. The `mutation-regression` label is set when the week's score falls more than 5% below the 12-week mean. A run that produced no readable report leaves the issue as it was. The staged report drops the source text Stryker embeds for each file and test file.

`weekly-fuzz.yaml` and `weekly-bench.yaml` treat each Go module as a unit: the root `go.mod` and every nested one that holds `.go` files, outside `node_modules`, `vendor`, `testdata`, `static` and `dist` (`scripts/go-units.sh`). So a repository made only of nested modules, such as cplieger/go, is covered module by module, and a nested module beside a root one is no longer skipped. Each unit builds with `GOWORK=off`, against the versions its own `go.mod` pins.

`weekly-gremlins.yaml` finds a repository's Go modules by the same rule, so a repository made only of nested modules gets a call, and one with no Go module gets none; one whose every module dir has a name `go-units.sh` skips still gets a call, which refuses those dirs. A repository with under about 200 lines (10,000 bytes) of non-test Go in its clone gets no call. The call measures the root first when it has a `go.mod`, then each nested module, and fails a repository it finds no Go module in. A repository whose every module dir is refused fails too, and its record names each refused dir with the reason. A call with a `module` input measures that module alone and names the others as untested in its result, its run summary and the weekly summary's `untested` column; untested modules neither pass nor fail the call.

`weekly-fuzz.yaml` fuzzes every `func Fuzz` target for 2 minutes, starting from the committed `testdata/fuzz/` corpus only. The runner is discarded and setup-go's cache is off, so the corpus a run grows is lost, and depth grows only through a failing seed someone commits. A module whose targets overrun one runner's 4-hour budget is split into shards, each fuzzing a fixed share of the targets, rather than given less time per target. Each new failing seed opens a `fuzz-finding` issue in the repository, and committing the seed under `testdata/fuzz/` closes it on the next run. A nested module's issue names the module in its title, `[fuzz] <target> (<dir>) regression — <hash>`, and only a seed inside that module closes it. A root module's issue keeps the plain title and is closed only by a seed outside every nested module.

`weekly-bench.yaml` benchmarks the modules its `ENROLLED` list names: a repository for its root module, or `<repo>/<dir>` for a nested one, such as `go/jsonx`. A dispatch's `only` input takes either form. Each enrolled module's medians go to `<dir>/data.js` on the repository's `benchmarks` branch (the root's stays at `data.js`), and each keeps its own `bench-tracker` issue: `Benchmark regression tracker` for the root, `Benchmark regression tracker: <dir>` for a nested module. The smoke job runs every benchmark of every module the list leaves out once, and fails when one does not run.
